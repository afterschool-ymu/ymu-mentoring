What this is

A complete system for running one-on-one music mentoring: matching Student Ambassadors to afterschool students, letting families choose their own session times, sending every reminder automatically, and tracking how each student is getting on. It runs entirely inside your own Google Workspace. Nothing to host, nothing to pay for.

Setup, step by step

About 15 minutes. Tick things off as you go — the boxes are just for following along, they reset if you reload.

  1. Create the spreadsheet

    A new Google Sheet in your YMU Drive, named YMU Mentoring. This becomes the database for everything.

  2. Open the script editor

    Extensions → Apps Script. This opens a project bound to your sheet.

  3. Paste in the code — three pastes

    Delete the default Code.gs. Then:

    ClickName itPaste
    + → ScriptCodeYMU-Mentoring-AllInOne.gs
    + → HTMLMentorPageMentorPage.html
    + → HTMLMenteePageMenteePage.html

    Names must match exactly, with no extension typed in. The all-in-one file is the twelve script files joined together — identical code, tested the same way. If you would rather keep them separate (easier to read, easier to change one thing later), the twelve individual files are in the same folder and go in as Config, Setup, Geo and so on.

    Don't paste the two -preview.html files — those exist only so you can see the screens on your own computer.

  4. Turn on the Calendar service

    In the left sidebar next to Services, click +, choose Google Calendar API, leave the identifier as Calendar, click Add.

    Don't skip this. Booking fails without it. It's what lets the script pass sendUpdates:'all' — the only reliable way to make Google email the invitation to guests when an event is created or changed.

  5. Run the setup menu, in order

    Reload the spreadsheet tab. A YMU Mentoring menu appears. Work down it:

    Google will ask you to authorise the script on the first run. The "unverified app" warning is normal for your own script — Advanced → Go to (unsafe). Read the permissions before allowing.

  6. Deploy the web app

    Deploy → New deployment → Web app.

    Description:     Mentor and student booking
Execute as:      Me
Who has access:  Anyone with a Google account

    Copy the URL it gives you. One URL serves both pages — it works out who's asking.

    Why those settings. "Execute as Me" lets the script write to your sheet on someone else's behalf. "Anyone with a Google account" hands sign-in to Google, so you never create or reset a password — and the code still checks every visitor against the roster before showing anything.

  7. Paste the URL into Config

    In Config.gs:

    webAppUrl: 'https://script.google.com/macros/s/……/exec'

    Save. This is what puts a working button in every reminder email, so nobody has to hunt for a link.

  8. Install the automation

    Menu → Install automation. Three triggers, and deliberately no more — Apps Script allows 20 per script, so anything per-session would break immediately.

    onFeedbackSubmitOn form submitFiles each response against the right session

    Run step 7 (create the form) before this, so the form trigger has something to attach to.

How the year runs

Seven sessions, October to April

One session a month per pair, an hour each. October and April are completely clear of holidays; December loses 10 weekdays and March loses 6 in a row.

Availability is collected two months at a time

Nobody is asked in September what they're doing next April. A mentor only ever sees, and is only ever blocked by, the cycle in front of them.

CycleOpensDueCollects for
C11 Sept 202612 Sept 2026October, November
C22 Nov 202613 Nov 2026December, January

C41 Mar 202712 Mar 2027April
Worth understanding: the cycle being collected is not the cycle whose sessions are running. In early November, C1's November sessions are still happening while mentors are being asked about December and January. Menu → Where is each cycle up to? shows exactly who has done what.

What happens when a cycle turns over

  • Cycle opense.g. 2 Nov Every mentor is emailed asking for their times, and pushed to keep the same days and times they've been doing.
  • Weeklyuntil the deadline Anyone who hasn't answered is asked again. Never daily — that's how people start ignoring you.
  • Deadline passesno reply Their existing pattern is carried forward onto the new cycle's valid dates, skipping holidays. They're told it happened and asked to check it.
  • Then re-checkedthe important bit A Tuesday-3:30 pattern that gave four October dates gives three in December once winter recess is out. If a month falls below the minimum, that mentor gets a "your availability is short — school holidays" email. This is the case that otherwise silently breaks a month.

School closures are hard blocks

The 28 non-student weekdays come from the Board-approved MDCPS 2026-27 calendar, cross-checked against the district's Technical calendar and reconciled against the published instructional-day counts (45+46+42+47 = 180) — which is how we know none is missing. Closed days appear on every calendar but can't be picked, labelled with the reason.

Add a school's own closure — a hurricane day, testing week, an event — as a row on the Closures tab with that school's site_id. Leave site_id blank for a district-wide day.

One thing to check with each school: every Wednesday, K-8 centres release grades 2–8 an hour early. That affects Fienberg/Fisher, West Little River and Henry Reeves. If it shortens their Wednesday programme, edit that site's hours — the district calendar can't tell us.

The rules it enforces

All of these are checked on the server, so a stale browser tab can't get round them.

RuleWhy
Instrument must match exactly
no exceptions		 A trumpet student can't be coached by a guitarist. This is the one hard filter in matching.
Sessions are 1 hour Changes which slots fit: Fienberg's 3:10–5:10 window holds two one-hour slots (3:30 and 4:00), not three half-hour ones.
At least 2 times per month, per school Fewer than two and a cancellation has nowhere to go. Mentors are asked for around 6.
Rescheduling needs 2 full hours still on offer A mentor whose only remaining option is the one they just vacated hasn't rescheduled — they've cornered the family. A student choosing a time is never blocked by this.
Cancelling requires a replacement Picking the new date is the cancellation. A freed slot nobody is watching is how a session gets lost. "None of these work" escalates to you instead, and the old booking holds until you agree a new one.
One pair per site per time slot Room availability. Booking a taken slot is refused by name: "already taken by Gabriel Bello-Diaz and Mentee 3."
Over 2 reschedules escalates to you Past that it stops being logistics and becomes a conversation about whether the pairing or the time of day is working.
No session without a supervising adult Stated in every calendar invite, in the day-of coverage check, and on the mentor's own page. Not negotiable.
No direct student-to-student contact Both are minors. Every message includes a parent and an adult; contact details are never exchanged, and guests can't see each other's addresses on invites.

Consistency is pushed everywhere

The first booking sets a pair's usual day and time. Every later month then leads with "Suggested: Tuesday 10 November at 3:30 — the same as your usual time" and a one-tap button. The mentor's form asks them to keep the same pattern, and the carry-forward only works if they have. The same afternoon every month is easier for a family to remember, easier for site staff to cover, and produces far fewer changes.

Plus the calendar invitation itself, which Google sends — and re-sends automatically whenever a date changes. That one costs nothing against your email quota.

A trap worth knowing about. Google treats calendar reminders as private per-user data. A "1 week before" reminder set by the organiser fires only for the organiser — guests get their own defaults. So these reminders are emails the script sends. Anyone who suggests replacing them with event reminders is wrong, and you'd discover it in November when no parent had been reminded.

Anything unrecognised is left visible in the email rather than silently vanishing, so a typo shows up where you'll catch it.

Feedback and reporting

The form asks who's filling it in, how the session went (1–5), how much progress the student is making (1–5), what they worked on, and anything YMU should follow up on. Its link carries a hidden session reference, so a response files itself against the right session and pair — nobody types a reference number.

A mentor's response also closes the session out. Anything in the follow-up box emails you immediately and shows on the dashboard. Menu → Feedback so far gives average satisfaction and progress per pair, for end-of-year reporting.

Still needs a decision from you

These aren't bugs. They're things the system can't decide, and two of them matter before October.

1. Instrument coverage doesn't match the programmes structural

The 16 ambassadors are a rock band — 5 Voice, 5 Guitar, 2 Keys, 2 Bass, 2 Drums. Six of the twelve sites run Jazz Afterschool or Marching Band, and there are zero trumpet, sax, trombone or violin mentors. Since instrument is the one non-negotiable rule, every horn student will land in the unmatched list, every cycle.

Either recruit horn ambassadors, or accept that Jazz and Marching sites aren't in scope this year. Rock sites you're well covered for: Nautilus, Fienberg/Fisher, Miami Beach Senior High.

  • Gabriel Bello-Diaz is in 8th grade, younger than some mentees. Confirm he's mentoring rather than being mentored.

Why it lives where it does

A reasonable question: does this have to be a Google Sheet with a script behind it, or should it be a "real" app?

The short answer: yes, you do have to do the setup once — nothing is live until you do. The HTML files sitting in your folder are documentation and previews. They cannot be the system, and no amount of work on them would change that.

Why a plain HTML file can never be the real thing

A file on your computer has no server behind it. That means it physically cannot:

  • Send an email. No reminders, no invitations, no nudges.
  • Run when nobody has it open. The 6am job and the feedback trigger need something awake at 6am.
  • Be shared. Fifteen mentors and their students all need to see the same data. A file on your laptop is one copy, on your laptop.
  • Know who is looking. No sign-in means no way to show Ella her student and not everyone else's.
  • Create calendar invitations.

Those five things are the system. So the question isn't HTML versus app — it's which server does the work.

It is an app, from where anyone else stands

Nobody but you ever sees a spreadsheet. A mentor gets a link, taps it, signs in with the Google account they already have, and sees a clean screen built for a phone. A parent taps a link and picks a time. Neither of them knows or cares what is behind it.

On a phone, Share → Add to Home Screen puts an icon on the home screen that opens straight to their page. It behaves like an app because, to them, it is one. No app store, no download, no password to forget.

Where the spreadsheet is an advantage, not a compromise. When something goes wrong at 4pm on a Tuesday — a student moves school, a mentor drops out, a site changes its hours — you fix it by typing in a cell. No ticket, no developer, no waiting. Very few custom apps give you that.

When you would outgrow it

Around 60–100 pairs the greedy matching would want replacing with a proper assignment algorithm, and the daily job would need to read in batches rather than scanning every row. Both are contained changes to code that already exists. Nothing about this design traps you: the data is in a spreadsheet, exportable to anything, and the rules are written in plain JavaScript you or anyone else can read.

At 15 pairs, and at 100, this is the right shape.

Cost

$0. Apps Script, Sheets, Calendar, Forms and Maps are all included in Google Workspace for Nonprofits, and the geocoding needs no API key. If you later want text messages to parents, Twilio is about 1.5¢ each but US sending requires A2P 10DLC registration — roughly $55 in year one on the 501(c)(3) charity rate, with 10–15 days for approval. Start that in September if you want texts by October.
